# Architecture

```
ruri.app (Electron)
  ├─ main process: startServer() in-process        ─┐
  │    └─ yagami AgentSession → Agent SDK           ├─ one WebSocket + static UI
  │       → your installed claude CLI               │  on one localhost port
  └─ renderer: React + Vite + zustand (dist-web)   ─┘  (shared/protocol.ts)
```

One HTTP server carries everything: `GET /healthz`, `GET /music/playlists`, `GET /music/track?p=…` (Range-capable), `GET /uploads/<file>`, the built UI on every other GET, and the WebSocket on the same port. `shared/protocol.ts` is the single wire contract — every client command and server message is a variant of `ClientMessage`/`ServerMessage`.

**Server**

- `server/server.ts` — importable `startServer()`: WebSocket hub + static file serving for the built UI; snapshot on connect, then statuses, permissions and finished turns to every window — but a chat's conversation as it happens (a reply's paragraphs, tool calls, agents at work, the turn's counter) only to the windows that have that chat on screen (the `view` message); a chat opened again is sent whatever it missed — the events themselves where a few arrived, the whole live transcript where the chat was compacted or rewound or more than two hundred events went by (`server/clients.ts`) — and nothing at all if nothing changed. Handles client commands, owns the model-probe cache and the app-side prompt queue (visible queued prompts and silent split sub-prompts alike).
- `server/sessions.ts` — per-session lifecycle. Claude sessions ride yagami's `AgentSession` (warm process, terminal parity, `appName: "ruri"`): SDK message → transcript event translation, permission plumbing (with the CLI's suggested "always allow" rules), model/permission-mode switching, resume-on-restart. A turn is whatever the CLI runs between its `system/init` and its `result` — including the ones it starts itself when a background task ends between turns (a task notice while idle holds the process open until that turn's `init`; the `init` makes the chat busy). Prompts go in with `--replay-user-messages`, so each is echoed the moment the CLI takes it up; a result that lands while a prompt is still unechoed belongs to a turn the CLI ran first, and is held (`finishTurn`) and folded into the prompt's own when that starts — released as is after 5 s if nothing does. Slash commands the CLI runs itself are not echoed, and are taken up by the next `init` instead. A chat's agent process closes, silently, the moment it has nothing left to do: its turn over, nothing of its own running in the background, and the chat not open in front of anyone — after a 3-second grace (`RURI_REAP_GRACE_MS`) that lets a queued prompt or an auto-retry claim it first. So a chat that finishes while you are looking elsewhere closes on its own, and an open chat's closes when you leave it (or after sitting idle ten minutes with it open, `RURI_IDLE_REAP_MS`). "Open" means open in a window someone is looking at: a warm CLI is 150-400 MB and goes on asking for the CPU for as long as it lives — enough, left overnight, for macOS to name ruri as using significant energy — and nobody is about to type the next prompt into a window that is behind another app. So a chat open only in sleeping windows is held for a minute (`RURI_ASLEEP_REAP_MS`) rather than ten: switching apps for a moment costs nothing, and walking away stops costing the battery. Waking a window puts its chats back on the long lease. Work in the background (a subagent, a shell the model left running) holds the process for as long as it runs, and its end is what lets it go — not a timer. The same work is counted for the UI (`backgroundWork`, sent as `work` per chat by `turns.ts pushWork`), which is how the sidebar and the projects page call a chat busy with no turn running. A shell the CLI reports in the background (`task_started` of type `local_bash`) becomes a card on its own tool chip, with where its output goes; an agent the CLI picks back up (a `task_started` for a task id it has seen, named by a SendMessage rather than a spawn) flips its card back to running — found by the CLI's id the card keeps (`agentId`), or by the agent's first words, and taken on from the chat's transcript when an earlier process started it. The next prompt resumes the same conversation from its session id, exactly as after a relaunch. Subagents are read off the stream as it comes: Claude sessions run with `forwardSubagentText` (and deliberately without `agentProgressSummaries`, which would fork every agent every 30 seconds to describe it), so every message with a `parent_tool_use_id` goes to that agent's log and the `task_*` messages move its card (`AgentBook`); Codex agents are matched to their card by the thread their `spawn_agent` call names. Non-Claude models route to `ProviderAgentSession`: yagami's agentic session layer (`openSession` — Codex app-server, ACP), the harness verbatim with tool chips and approval cards; `ProviderTurnSession` (one sandboxed `provider.run()` per turn) remains as the fallback for providers without it. Both use provider-prefixed resume ids streamed into the same events. A `ProviderAgentSession` turn whose harness process dies before saying anything (`sendStarting`: "connection closed", "exited with code", "database is locked" — never sign-in or not-installed) reopens the process on the session it had, a fork already made not made again, and sends the same prompt, twice at most (`START_RETRY_MS`), unless the user has stopped the turn.
- `server/agents.ts` — `AgentLogs`: each subagent's own log, apart from the chat that started it — written on a debounce, held in memory only while writes are pending, capped at its newest 1500 events, and gone with its chat. `Crew`: the agents the user starts from a chat's agents page — each card and the harness session a follow-up resumes, one `@crew.json` per chat beside the logs; they run on a `SessionManager` of their own in server.ts, keyed by their card's key, so nothing that watches the chats (status, queue, retries, recall notes) ever sees them — only the chat's background-work count, which is what keeps its row busy in the sidebar while one works.
- `server/scripts.ts` — a background script's page on the agents page: its command, and the tail of the file the CLI writes its output to (only a task-output path under a `tasks/` directory is ever read), read afresh each time the page asks.
- `server/updater.ts` — `HarnessUpdater`: every coding CLI on the machine (yagami's detection), what version it is (read off its install path where it can be — claude's `versions/<v>`, a global package's `package.json`, brew's Cellar — else `--version`), what the newest is (the npm registry, or brew's tap data), and on the hour — never under a chat that is mid-turn on it — the update, the way it was installed: `claude update` / `opencode upgrade`, `bun add -g`, the npm of the prefix the package lives under, `brew upgrade`. An updated harness's warm sessions retire as each goes idle. Harnesses set to update by hand are looked at, not touched.
- `server/integrations.ts` — MCP servers, plugins and marketplaces for Claude Code and Codex. Claude's servers are read from `~/.claude.json` (user and local scopes, a project under its real path) and a project's `.mcp.json`, plugins' from `claude plugin list --json`; Codex's from `codex mcp list --json` and `codex plugin list --json` — nothing is started to list it. Changes are the CLIs' own commands. Environment and header values never leave the server, only their names. `handlers/integrations.ts` retires the changed harness's warm sessions as each goes idle.
- `server/blocked.ts` — what a failed turn was up against when it was the world's doing: `blockedBy` reads a dropped connection (`network`) or a spent usage limit (`limit`) from the harness's words and HTTP status (a Claude session also takes the CLI's own `rate_limit` flag and rate-limit event, which says when the limit lifts). A blocked result holds the queue with that reason instead of draining it (`holdForTheWorld` in `server/dispatch.ts`). `ConnectionWatch` probes the API's host (`ANTHROPIC_BASE_URL`'s when set) every ten seconds while anyone waits on it — a held queue, to say the line is back; a dropped turn's retry, which goes only then.
- `server/paragraphs.ts` — `ParagraphGate`: holds a streamed reply back until a paragraph is finished (a blank line, or a code block closing) before it goes to the window, so a reply arrives a paragraph at a time rather than a token at a time.
- `server/finder.ts` — finding a project folder by the name a person uses for it: walks the workspace root, scores folder names against what was said, prefers folders that look like projects. Behind Home's `find_project` tool.
- `server/ledger.ts` — `LedgerStore`: what each project has spent, by the day — tokens, dollars at API prices, turns, wall time — added to as results land and never pruned. Behind the board's figures.
- `server/recent.ts` — the chats that happened outside ruri: lists a project's Claude and Codex session files by working directory, and reads one into transcript events for import.
- `server/manager.ts` — the Home agent: an in-process MCP server (`find_project`, `open_project`, `new_project`, `hide_project`, `unhide_project`, `close_project`, `list_projects`) plus a workspace-manager system prompt, layered onto a normal session at the workspace root. Non-Claude harnesses get the same duties via a system-prompt-described drop file (`.ruri/open.jsonl`) drained at end of turn.
- `server/homelog.ts` — Home's write-ahead log: appends each Home event as a greppable one-liner under numbered, dated SESSION headers; the model reads it (via search), never writes it.
- `server/providers.ts` — `ProviderRegistry` over yagami's provider layer: detects the installed harnesses once at startup (honouring `~/.config/yagami/config.json`), lists their models for the picker as `provider:model` ids, and builds per-project provider instances working in the project directory.
- `server/projects.ts` — `ProjectStore`: projects, their sessions, and the device-wide settings (workspace root, music dir, Home's model/mode, starred models, the small-tasks model), persisted to `projects.json`.
- `server/archive.ts` — `SessionArchive`: transcript events, per-turn recall notes, the resumable session id, a rewind's fork point (with the session it is a point in — handed only to a build resuming that session, and dropped when the chat moves to another), and a pending compaction brief per session, debounce-written to disk (compact JSON, written beside and renamed over). The source of truth behind the connect snapshot — which carries only the last few events of each chat; a chat asks for the rest when it opens (`transcript_get`), and the window keeps a handful whole at a time — and `/compact`. Each transcript is two files: the live part from the newest compaction mark (`sessions/`), and the history before it (`history/`, JSON Lines, appended to by a compaction and read only for a rewind or fork reaching back past the mark, a brief, or an earlier exchange opened in full — the chat itself gets an outline of it, a line per exchange, cached until the file changes). An archive from before the split is split once, the first time it is loaded; the history is capped at 16 MB (`RURI_HISTORY_MAX_BYTES`), oldest exchanges first, read a chunk at a time rather than whole so a file that size is never also a string that size. Where each live event sits is kept as a map from its id, rebuilt whenever anything moves them about, so adding one does not scan the conversation first.
- `server/commands.ts` — slash commands inside a prompt: which names count (ruri's own, the harness's, every installed skill and custom command), the lift that runs them ahead of the prompt they were written in, and the described list the composer's menu offers.
- `server/checkpoints.ts` — ruri's own file checkpoints: the working tree as a hidden git commit as every prompt goes out and again as its turn ends, on every harness, each with HEAD and every branch and tag written into its message; and the rewind that takes the discarded turns' changes back out of the tree as it stands (a line merge where something else changed the same file since) and puts back the refs they moved, where nothing they would drop has been pushed. `server/handlers/rewind.ts` decides the conversation's side — a native fork at the kept exchange, a brief, or a fresh start — and sets the context gauge back to the reading the kept exchange left (`contextAt` in the archive).
- `server/compaction.ts` — ruri's own `/compact`: writes each exchange's full record and attachment paths to `turns/<session>/NNN.md` and builds the model-facing brief out of the precomputed recall notes as prompt/reply pairs, one file hook per exchange. No model call — it's instant. The brief lists at most 40 exchanges (`RURI_BRIEF_LISTED`); older ones are folded into the **digest**, one condensed memory the small model keeps (`DigestFolder`, run in the background after each reply's note and when a chat opens — each fold takes the list back to 30). The brief opens on it and names the record files it covers, so nothing folded away is out of reach. Ahead of all that goes `<state>` — git's account and the files the conversation changed, from the transcript's diffs — and the last three exchanges go at length (`<recent>`) rather than as notes; `relevantBlock` adds, as the brief goes out, the exchanges and memory lines that share the next prompt's words (`server/recall.ts` ranks them).
- `server/smallmodel.ts` — the small-tasks layer over yagami's completions client: prompt and reply recall notes, session role titles, prompt splitting, tracker extraction, plus `TurnTracker`, which assembles prompt→result turns out of the event stream. Every call is a CLI process, so they take turns — two at a time across the app (`RURI_SMALL_AT_ONCE`) — and Codex runs through a wrapper (`~/.config/ruri/bin/codex-small`) that adds `--ignore-user-config` to `exec`: a completion needs none of the MCP servers the user's `config.toml` would otherwise start for it, which measured 463 MB across nine processes per call against 167 MB across three.
- `server/tracker.ts` — `TrackerStore`: the per-session feature checklist, auto-extracted or hand-added.
- `server/uploads.ts` — attachment intake (images, videos, arbitrary files): base64 in, files under `uploads/` and small URLs in the transcript, region crops expanded into extra model-visible images, a picture of a type the model can't take (SVG, BMP, …) swapped for the composer's PNG of it plus the original's path, non-image files referenced by path in the prompt. Also the sweep that removes uploads nothing mentions any more (after a day's grace), at launch and twice a day.
- `server/orphans.ts` — the launch sweep for what closed sessions and projects left behind (an archive, a history, turn records, bridge screenshots, a checkpoint index), read against projects.json itself; nothing goes unless that file reads cleanly, and nothing touched in the last ten minutes.
- `server/usage.ts` — the account limit windows behind the dragon gauges: Claude's from the OAuth usage endpoint (token from the keychain, or the credentials file), Codex's from the `token_count` entries in its session rollouts, each with the percentage used and when the window resets. Polled every five minutes and after every turn, cached to `usage.json` so a relaunch opens on the last good reading; all best-effort — an unreadable source just leaves that harness's gauges empty.
- `server/music.ts` — the music library scan (folder = playlist, loose files = "Unsorted") and the path allowlist for the track route.
- `server/index.ts` — standalone entry for dev/smoke (same server, no Electron).

**Desktop & UI**

- `desktop/main.ts` — Electron main: login-shell PATH recovery (async, alongside Electron's own start-up), window/menu/lifecycle — a quit waits up to five seconds for the bridge and the server to close so debounced transcript writes land; new windows and navigations off the app's origin are denied and sent to the default browser (http, https and mailto only) — the native folder picker, and the cursor poll that drives the titlebar peek hover; esbuild bundles it together with the server, yagami, and the Agent SDK into a single file (`scripts/build-main.ts`).
- `desktop/permissions.ts` — the nine macOS grants ruri uses, each read as macOS holds it, asked for by hand from Settings, and — for an ad-hoc-signed build only — asked for again on the first launch of a new build (`docs/permissions.md`).
- `web/src/store.ts` — zustand store fed by the socket; drafts (a reply in progress, arriving a paragraph at a time) are kept separately from finalized transcript events. It tells the server which chats are on screen (`watchChannel`, `watchBoard`; nothing while the window is hidden), and a chat sent whole again keeps every unchanged event as the same object, so catching up re-renders only what moved.
- `web/src/components/ChatPane.tsx` — the chat pane itself: resolves the channel and project, watches it, and mounts a `ChatView` keyed by the channel so every per-chat piece of state resets by construction when you switch. The parts it used to hold in one file are their own now: `Exchange.tsx` (turn grouping, folding and compaction marks), `EventView.tsx` (one event: prompt, reply, tool chip, result line), `Composer.tsx` (the prompt box, attachments, model and effort picks), `Queue.tsx` (the drag-reorderable prompt queue), `PermissionBanner.tsx` (permission and question cards), `SessionControls.tsx` (the header's buttons), `AgentsPage.tsx` (the agents list and an agent's own conversation), `Confirm.tsx` (the in-app confirm card that replaced `confirm()` and `alert()`), and `components/chat/` for the icons, agent card and empty states they share. A long session is kept cheap to switch into: the tail paints first and the rest fills in on idle frames, every re-bottoming folds into one layout read per frame, and every turn above the last four gets `content-visibility` so the browser lays out what you're looking at rather than the whole history.
- `web/src/components/RapidFire.tsx` — rapid fire: the client-side line of prompt-ready sessions, the hand-off timing, and the header bar. It renders no pane of its own — the chat pane takes the session it picks.
- `server/brief.ts` — the project's sheet: the store (per project) of its shape — the stack, each layer with its handle and the paths it owns, and each layer's own sheet — and its working memory, the user's corrections to both, which layer a file belongs to (the longest owning path), and what it writes into each project: `.ruri/architecture.md` (the index — the stack with each layer pointing at its sheet, the flows across layers, layout, how to run it, conventions, features, and the commit the repo was read at; an older sheet without layer sheets leads with where to change what instead), `.ruri/layers/<handle>.md` (a layer's where to change what, how it works, key files, rules and traps, what it talks to), `.ruri/catchup.md` (git's account, where the work stands, decisions and why, what worked, what didn't and why, gotchas, what's open — each line with its date, its exchange's ref and its author), and the stack as every session is shown it (`stackBriefing`, rides in `server/briefing.ts`).
- `server/catchup.ts` — the reads of the repo: the index from the README, manifest, Makefile, agent instructions, tree and file openings; too-big layers cut into their parts and unowned files placed (`splitBigLayers`, `placeUnowned`); each layer's sheet from the paths it owns and its central files (`buildLayerSheets`). `server/events.ts` folds a project's finished turns into the index and, layer by layer, into the sheets of the layers whose files they changed (`foldLayers`).
- `server/memoryLines.ts` — the memory as lines with ids, sources, authors and pins: reading an older ruri's strings, laying a fold's answer over the memory (kept lines by id, exactly as stored; only the model's own reworded; pinned ones back where they were), a line added from outside, and a fold rebased over what changed while it ran.
- `server/memoryCli.ts` — the memory from a session's shell, on the same `ruri` command and endpoint as the library: `note`, `memory`, `forget`, `state`, `recall`, `recall show`, and `layer` (the stack, or one layer's sheet).
- `server/recall.ts` — an exchange whole (its prompt, reply, tools and changed files, numbered as its history numbers them), and BM25 over them: `ruri recall` across a project's chats, and the brief's pick of what bears on the prompt it rides with.
- `server/gitState.ts` — where the repo stands, read from git with optional locks off (the branch, what's uncommitted, what's unmerged, the last commits, commits since a read), and what git says of the branches a line names.
- `server/handoff.ts` — what the app adds to a compaction brief (git's account; what bears on the next prompt), and the check before a prompt resumes a Claude session that the session and its fork point are in Claude's own transcripts — letting go of one that isn't (and of a dead process still holding it), for a brief, rather than failing every prompt after. When a resume fails anyway ("No conversation found", "No message found with message.uuid"), the session hands its untaken prompts back (`SessionEvents.onLostStart`) and `recoverLostStart` sends them again to a fresh, briefed session.
- `server/memory.ts` — the working memory written whole from a project's chats: each one's digest, recall notes and last replies, read once for a project that has history and no memory, and on request.
- `server/catchupBrief.ts` / `web/src/components/Architecture.tsx` — the sheet pushed into the project and to every window as it changes (with each memory line's source and git's account, and again shortly after every turn ends), the reads of the repo and the chats run and reported, memory refs resolved both ways, and the architecture page that draws the shape — each stack bar opening its layer's sheet — and takes the user's corrections to it.
- `server/ruriDir.ts` — the project's `.ruri/` folder: made self-ignoring, and kept out of a project that is still blank so scaffolders will run there.
- `server/catchup.ts` — the shape written whole: reads a repo the way a person joining it would — every source path by folder included, so the map of where to change what names real files — and has the small model write every section at once, layers, flows and map included; the commit it read is kept, and the page says how many commits ago that was. Runs for a project that arrives without a sheet, for one whose sheet predates layers, and on request.
- `server/briefing.ts` — what every project session is told about ruri before it starts: the catch-up file, `ruri note` / `ruri recall` / `ruri state`, the component library and the `ruri` command, the vault. Pointers, never contents — none of it costs a token until the model opens it, and none of it changes when they do.
- `web/src/components/Ideas.tsx` / `server/ideas.ts` — the ideas board.
- `web/src/components/Components.tsx` / `web/src/components/NameCard.tsx` / `server/components.ts` — the component library: the gallery and each component's page with its code, the naming card and its screenshot, the store (handles, a component's own files apart from the places it reaches, the folder installs go to, the one-time move from the old index that sets backend entries aside), the naming tools, the `.ruri/components.md` it writes, and the entries it hands to a prompt that names one.
- `server/library.ts` / `server/handlers/components.ts` — the library from an agent's side: the `ruri` command (a few lines of sh in `~/.config/ruri/bin`, on every project session's PATH, posting to `POST /library/<chat>`) and everything it runs — search, show with code, add (a copy into the project's components folder, from this project's library or another open one's), register, edit, remove — plus what counts as interface, reading a component's files, and the `ruri:components` skill written per project into `~/.config/ruri/library/<projectId>/` and handed to Claude sessions as a plugin.
- `server/sweep.ts` / `server/shots.ts` / `desktop/capture.ts` — the repo sweep: which files are worth reading and what the small model is given of each (the top of it, what it exports, every class it sets), then the project's dev server started and stopped around a hidden window that finds each selector and captures its rectangle.
- `server/libraryRefresh.ts` / `server/photographer.ts` — keeping the library true to the code: entries' files followed through git's renames or retired when gone, the commits and uncommitted edits to each entry's own files since its picture and note were current, and the prompt of the "Library pictures" chat that photographs what the mechanical pass can't reach. `handlers/components.ts` runs the whole refresh behind **Update everything** — files, changes, naming, the small model's review (`reviewComponents`), pictures.
- `server/talk.ts` / `server/handlers/talk.ts` / `web/src/components/TalkPage.tsx` — agents talking to agents: the rules for who may message whom (`~/.config/ruri/talk.json`) and how they resolve, the handles chats address each other by, the words each side reads, the book of messages in flight, the `list_agents` / `message_agent` tools on the `ruri` MCP server and `POST /talk/<id>` for other harnesses; the handler side sends (limits, the card outside Bypass, into the other chat's line), settles each message when the turn it started ends, and the talk page edits the rules.
- `server/bridge.ts` / `desktop/bridge.ts` / `server/cdp.ts` / `desktop/apps.ts` / `web/src/components/Bridge.tsx` — the bridge: the tool definitions and their two faces (in-process MCP server `bridge` for Claude, `POST /bridge/<channelId>` for every other harness) and the session briefings, in `server/bridge.ts`; the harness-neutral DevTools-protocol driver (find/click/type/press/scroll/screenshot/logs/wait, over either Electron's `webContents.debugger` or a raw `ws` socket) in `server/cdp.ts`; the per-channel hidden windows, previews and take-over in `desktop/bridge.ts`; the macOS app launching, Accessibility UI scripting and window-server captures in `desktop/apps.ts`; and the preview strip above the composer in `web/src/components/Bridge.tsx`.
- `web/src/components/NameCard.tsx` — the card that asks what to call the thing the model just built.
- `server/secrets.ts` — the vault: storage, the environment it exports, the `{{handle}}` substitution, and the redaction that puts handles back.
- `web/src/components/Skills.tsx` / `server/skills.ts` — the skills page and the bmo/filesystem layer under it.
- `web/src/components/Statistics.tsx` — Home's other page: what all of this has cost (the ledger's three spans, and a row per project), what is running (the agents, off `server/resources.ts`), and what is left (the usage windows, written out from the composer's gauges). It used to be the top strip of the projects page, which made that page two questions at once; they are separate pages now, and the projects moved to their own row in the sidebar.
- `web/src/components/Capped.tsx` — a list that stops growing: past its item count it holds at that height and scrolls, half the next item showing. Every open-ended list inside a longer page wears one — Settings' integrations, models, vault and harnesses, the skills, the statistics tables, a project card's chats.
- `web/src/components/figures.ts` — how a number is written: money, token counts, spans of time. Shared by the projects page and the statistics page, which were one page until they were two.
- `web/src/components/Terminal.tsx` / `server/terminal.ts` — the composer's shells: xterm.js over a pty, a row of tabs per channel, with the row persisted to `~/.config/ruri/terminals.json`. A shell's scrollback is kept as the chunks it arrived in (`server/scrollback.ts`), so a build printing hundreds of lines a second costs what it just printed rather than the whole 200 KB budget each time.
- `server/resources.ts` — what the agents are costing this machine, for the statistics page. One `ps` gives every process; the ones descended from ruri are rolled up into the things that started them, so a harness and its MCP servers are one agent rather than six rows. An agent is a process ruri can name a chat for — from a session id on its command line (a resumed harness is told which to continue, and the archive knows whose that id is) or from the chat id ruri put in its environment when it started it (`tagged` in `server/chats.ts`, which is the only thing that can place a *fresh* conversation). Everything else under ruri — the probes that ask each harness what models it has, the shells behind the terminal tabs, a stray `git` — is counted in ruri's own figure rather than called a chat. Nothing is sampled unless a window has the page up (the `view` message's `meters` flag).
- `server/relay.ts` — a shell's output on its way out, paced by what each window can take: a window with room takes its chunk at once, one that is behind has it joined onto what is already waiting and takes the lot in one message when its buffer drains, and a tab every window is behind on has its pty paused until one catches up. A socket that has stopped draining entirely is closed, and the window reconnects to a fresh snapshot.
- `web/src/tuner.tsx` / `web/src/peek.ts` — the art tuner and the placements it writes; the hero face and the peek band start from the latter.
- `web/src/lib/greetings.ts` / `web/src/greetings.ts` / `web/src/components/GreetingEditor.tsx` — what Home says over its empty chat: a list of lines taking turns a launch at a time (`pickGreeting`), a stored list read back (checked); the window's copy, kept as the `ruri-greetings` preference (a list the retired hero face kept in `ruri-hero` is read until the first change moves it); and Settings → Greeting, which edits it.
- `web/src/components/EmptyTop.tsx` — what sits over a chat with nothing in it yet: a project chat's title, or Home's greeting.
- `web/src/pictures.ts` / `web/src/lib/effects.ts` — the peek band's pictures: the user's own kept as uploads (`store_picture`), fetched once, known to move or not, and the frame each should show (`useShown`); the ten hovers and how a moving picture moves.
- `web/src/lib/peekBand.ts` / `web/src/band.ts` — the peek band: what a picture in it is and the hovers it can have, the default band, a stored band read back (checked); and the window's copy of it, kept as the `ruri-band` preference, with each picture's bytes, whether it moves and its first frame.
- `web/src/components/PeekBand.tsx` / `web/src/components/BandEditor.tsx` — the band across the sidebar's top, one picture drawn the same way there and in Settings, and the editor that places them. While ruri is the window in use the band is no drag region at all — every picture sees the pointer — and a press anywhere on it carries the window itself (`window_drag` → `desktop/main.ts`); behind another app it is the title bar again, dragged natively.
- `web/src/components/Dragon.tsx` / `web/src/dragonArt.ts` — the four gauges flanking the composer: the traced dragon art, the waterline that clips it, the reset countdowns, and the harness whose windows each session reads.
- `web/src/components/HomeBoard.tsx` — Home's tab strip (chat / projects) and the projects page: a card per project with live activity lines and its spend, and the head that adds every project up.
- `web/src/components/Sketch.tsx` — the sketch pad: a shapes-based canvas with pen, arrows, boxes, ellipses, placed text; saved as it is drawn; attaches to the prompt, or draws on an attached picture and puts it back.
- `web/src/components/CommandMenu.tsx` — the composer's `/` menu: every command that would run, found by typing.
- `web/src/components/Markers.tsx` — the composer's markers and commands as chips: a mirror of the prompt over the textarea, drag to move, click to open or take out.
- `web/src/components/Selection.tsx` — the selection flags: a draggable flag at each end of a transcript selection, with edge scrolling.
- `web/src/components/Sidebar.tsx` — Home and rapid-fire rows, project folders and their sessions, the peek band, the account bar.
- `web/src/components/Settings.tsx` — a page (it outgrew being a dialog), in groups: appearance, folders, the vault, and the searchable model catalog. The page is the only thing that scrolls — nothing inside it has its own scrollbar — and every value starts at the same left edge.
- `web/src/press.ts` — pointer capture on every pressable thing, so a press that starts on a button ends on that button however far the press animation moves it; a release well away from it still cancels.
- `web/src/lib/beat.ts` — the clocks for everything that moves by itself: the thinking doodle, the sidebar's dragon heads (two steps, `data-chomp`), the streaming cursor, an agent's ring (the Home board's status dots hold still). There are no infinite CSS animations anywhere in the app: each one had Chromium redraw the window at the display's rate, up to 120 frames a second, for as long as it was on screen. There is one clock per pace, and each ticks only as often as its movers actually change: the doodle, the dragon heads and the cursor share a half-second clock, and the agent ring has its own at 15 steps a second (thirty to a turn, a turn every two seconds). A tick writes only the elements whose step changed, and each mover is its own compositor layer, so a step repaints nothing on the page. The clocks run only while ruri is awake (`lib/awake.ts`), and only for movers actually in view: an element scrolled out of the viewport or on a page that is not showing takes no steps, and snaps to the clock's current step when it comes back. Asleep, everything holds where it stands and every counting clock (`useNow`) waits. The music waveform and notes use the same gate at 15 Hz, the new-component star (`lib/spin.ts`) at 10, turning on its own layer.
- `web/src/lib/awake.ts` — whether anyone can see ruri: the window on screen and the one in use. Asleep — behind another app, minimised, hidden — nothing on it moves: the clocks stop where they stand and every running Web Animation pauses, to pick up on waking. That is all sleep is. State keeps flowing exactly as when awake: the server keeps sending live, every message applies the moment it arrives, transcripts and the board stay current, and the agents behind them are never touched — so the window is already right when you come back to it, and nothing has to catch up. `?awake` in the URL (`RURI_AWAKE=1` for the desktop app) keeps a window awake for scripts that drive it from behind.
- `web/src/components/Player.tsx` + `web/src/lib/audio.ts` — the sidebar player and its two-deck Web Audio engine.
- `web/src/components/Attachments.tsx` — composer thumbnails, the full-size viewer, and drag-to-annotate region crops.
- `web/src/markdown.tsx` — marked + DOMPurify + highlight.js markdown renderer shared by messages, streaming drafts, and plan cards. Finished text is cached by its own string, so a session you've read re-renders from HTML; a reply still being written skips the cache, since every prefix of it is thrown away, and only changes when a whole paragraph arrives, so the window re-renders a few times per reply instead of once per token. A reply being written renders only the paragraph that just arrived: a closed fence at the margin followed by a blank line is a point nothing later can reach back past, so the HTML before it is rendered once and kept (`createStreamingMarkdown` in `web/src/lib/markdownHtml.ts`), and a reply holding a link reference definition or a raw HTML block falls back to being rendered whole.
- `web/src/lib/highlighter.ts` + `web/src/lib/highlight.worker.ts` — who highlights a code block, and where. A block is remembered by its language and its text, which never change once written, so the second render of one is a map lookup; a block over 2 KB goes to a worker and the plain text on screen is replaced where it stands when the answer comes back. A render still waiting on a worker is not cached, by either the markdown cache or the streaming renderer's kept prefix.
- `web/src/fixture.ts` — the canned `?fixture` state used for token-free UI work.

## Where things live

All app state sits under `~/.config/ruri` (move it wholesale with `RURI_CONFIG_DIR`):

| Path | What |
|---|---|
| `projects.json` | Projects and their sessions, workspace root, music dir, Home's model/mode, starred models, small-tasks model, default model |
| `sessions/<sessionId>.json` | Transcript events since the newest compaction, per-turn recall notes, resumable session id, pending compaction brief |
| `history/<sessionId>.jsonl` | Every event before the newest compaction, one per line — capped at 16 MB, oldest exchanges dropped first |

| `components/<projectId>.json` | The component library, and the folder `ruri add` installs into (`<projectId>.not-ui.json` beside it: entries the old index held that were no interface) |

| `ledger.json` | What each project has spent, by the day — the board's figures |

| `prefs.json` | The window's own preferences: theme, the theme clock, unfolded folders, the player's volume |
| `terminals.json` | Which shell tabs each project had open |

Inside each project ruri keeps a `.ruri/` folder, which ignores itself (one `.gitignore` saying `*`, so none of it shows up in your `git status`): `catchup.md` (where the work stands), `architecture.md` (the project's shape, as an index of its stack), `layers/` (a sheet per layer of the stack) and `components.md` (the component library) for whatever harness is working there, and `open.jsonl` at the workspace root for Home. A project folder that is still blank — nothing in it but what `create-next-app` will build around (`.git`, `.gitignore`, `LICENSE`, editor folders) — gets no `.ruri/` at all, and one left there before is cleared as a prompt goes in, so a scaffolder or a `git clone` finds the folder as you left it; the turn that gives the project something real writes the files that were held back (`server/ruriDir.ts`).

Everything else is yours and untouched: `~/.claude` (settings, CLAUDE.md, skills, hooks, the CLI's own session files) — except that turning a skill off in the Skills page moves its folder to `~/.claude/skills-off/` and back — `~/.codex/config.toml`, `~/.config/yagami/config.json`.

## Security model

The app is a local server and one window on it; these are the lines it holds.

- **Loopback only.** The server binds `127.0.0.1` (port 7776 for the desktop app, 7777 for `bun run dev`); nothing listens on an interface another machine can reach.
- **A token per launch.** The server mints a random token when it starts and hands it to its own window. Every WebSocket connection carries it in `?token=`; a connection without the right token is refused (compared in constant time). The server also writes it to `<config dir>/token` (mode 0600, removed on close): under `bun run dev` the page fetches it from the Vite server's `/__token`, which reads that file and answers only same-origin requests, and the test scripts set `RURI_TOKEN` for the server they spawn. State-changing HTTP routes (uploads, the bridge, anything with a side effect) carry it in an `x-ruri-token` header; `GET` routes that serve the UI and its static files do not need it.
- **Origin pinned.** A connection's `Origin` header must be absent (a non-browser client, such as the test scripts) or the app's own origin (`http://127.0.0.1:<port>` or `localhost`, plus the Vite page's `localhost:5173` under `bun run dev`); a page on any other origin open in the same browser cannot open a socket to ruri.
- **Talk is capability-keyed the same way.** `POST /talk/<id>` speaks as the chat whose id it is given, so the other chats are never named by id: `list_agents` hands out handles, a salted hash of the id that changes every run.
- **The bridge is capability-keyed.** `POST /bridge/<id>` — the harness-neutral face of the bridge, for CLIs that cannot carry ruri's in-process MCP server — takes the session id as its capability: only a process ruri itself started with that id in its environment knows it.
- **Vault secrets never reach a terminal.** The vault's values are exported only into the environment of harness processes ruri spawns (`$RURI_SECRET_*`, and `{{handle}}` substitution at the tool boundary), redacted back out of the transcript by handle. The composer's shells (`server/terminal.ts`) are started without them.
- **The wire protocol is validated at the boundary.** Every `ClientMessage` off the socket is parsed with the zod schema in `shared/clientSchema.ts` before it is acted on — the schema is typed against `ClientMessage`, so a schema that drifts from `shared/protocol.ts` fails `tsc`; a message that does not match is dropped with an error to the sender, never partially applied.
- **Signed, not notarized.** The bundle is signed with a local self-signed identity (`ruri dev`, see `docs/permissions.md`) so macOS privacy grants survive rebuilds. There is no Apple developer account behind it, so it is not notarized; it is installed by `make`, never downloaded, and Gatekeeper is not involved.
- **A Content-Security-Policy on the built page.** `vite.config.ts` stamps a policy into the built `index.html`: scripts only from the app's own origin (the built page has no inline script), images and media from there or from `blob:`/`data:` URLs the page made itself, no plugins, no `<base>`, no form posts. A model's markdown cannot pull a script, a frame or a tracking pixel from anywhere else. The dev page goes without it, since Vite injects an inline preamble.
- **Dev-only endpoints check their caller.** The Vite dev server's tuner endpoints, which write `web/src/peek.ts` and PNGs under `web/public`, accept a POST only from the dev page's own origin.
