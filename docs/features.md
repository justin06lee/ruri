# What ruri does

The long form of the README's summary — one bullet per capability, in the order they were built. `docs/architecture.md` says where each lives.

- **Native desktop app** — `ruri.app` with Dock icon, single-instance, inset title bar; the window serves the UI and WebSocket from one local port picked at launch.
- **Home — the workspace agent.** The default view (and the pinned Home row) is a session that manages the app itself: tell it "today let's work on X, Y, Z" and it finds the matching directories under your workspace root, opens them in the sidebar, and can kick each session off with a delegated first prompt. On Claude that happens through a handful of in-process MCP tools, one plain thing each and always by the project's name: `find_project` (where a folder of that name lives under the workspace root), `open_project`, `new_project` (a fresh folder under the workspace root, opened), `hide_project` / `unhide_project` (tucked under the sidebar's hidden fold, still open), `close_project` (the sidebar entry and transcripts go, never files), and `list_projects`; on any other harness Home drops the same requests as JSON lines into `.ruri/open.jsonl` at the workspace root (`path`/`kickoff` to open, `new`, `hide`, `unhide`, `close`) and ruri applies them as the turn ends — so Home orchestrates on whatever model you point it at. A project opens once: the same folder by another spelling of its path (a symlink such as `~/Workspace` onto an external drive, another letter case, a path relative to the workspace root) or another folder answering to an open project's name — a backup, a worktree, a second clone — is the project already open, so Home is told "already open", nothing new appears in the sidebar, and a kickoff goes to the open one. The workspace root is configurable from Settings; deep work happens in each project's own session, Home just orchestrates. Its chat is deliberately ephemeral — every app launch starts it blank, and navigating away and back wipes it too (a running turn finishes first): it's a dispatcher, not a place to accumulate context. It also keeps only its newest 50 events: older turns fall away as new ones arrive, cut where a prompt starts. What persists instead is its **write-ahead log** (`~/.config/ruri/home-log.md`): every prompt, tool call, and reply is appended programmatically as the events stream — the model spends no tokens writing it — in per-session blocks headed `SESSION <n> — YYYY-MM-DD (Day) HH:MM`. Home is told that file is its memory and to *grep* it for dates and keywords when you refer to earlier work, never to read it whole. It also skips the header bar — nothing between the titlebar skyline and the conversation. When you name a project, Home looks it up rather than guessing: `find_project` walks the workspace root from Settings by folder name, fuzzy, stopping a couple of levels into any repo it meets (a monorepo's packages count, its source tree does not), and answers with paths marked as projects when they hold a repo or a manifest; on the drop-file harnesses the prompt says to `find` the same way. Home is two pages under one strip of tabs — **chat** and **statistics** — so the agent and the figures never crowd each other; the strip remembers which you were on, and the chat tab carries Home's own dot, so a turn left running shows from the other page. The two sit side by side: picking the other slides the strip's inked pill across to it and the pages past each other, the one you leave going out one side as the other comes in, while the strip itself stays where it is.
- **Projects — every open project at a glance.** Its own row in the sidebar, under Home: a card per project, the live ones first, with a status pill and three live lines of what each session is doing (a streaming reply's tail moves as it streams, a tool call shows the moment it's made). The head says how many there are and how many are working or waiting on you. A project is working for as long as anything in it is — a turn, or, with its turn over, an agent or a script it left running in the background; its card says so in a line of its own ("an agent at work in the background"). A live card lists only the sessions that make it live — working, waiting on you, errored — not the chats beside them that finished hours ago; an idle card, with nothing live to show, shows where each of its chats left off. Click a card to land in that session. The row carries the count, and nothing about what the projects are doing: every session says its own state where it is, under its folder in the sidebar and on the cards here. **Tab** flips between this page and the Home agent's chat, whenever nothing else wants the key (a field that tabs between answers, a shell, the command menu completing a name); the caret goes back into Home's box on the way back, so a thought left there carries on.
- **Statistics — what all of this is costing.** Home's other tab, in three parts. *What it has cost*: dollars, tokens, turns and time for today, this week and all time, then a row per project, heaviest first — off a ledger (`~/.config/ruri/ledger.json`, one bucket per project per day), which is what keeps the figures true across rewinds, compactions and Home's own amnesia; the result lines in a transcript are where a turn's cost is shown, never where it is counted. *What is running*: every chat with a harness process alive, named as that chat, with its resident memory (its MCP servers counted in), its share of a core, how long it has been up and its pid — click a row to land in that chat. A warm harness is 150–400 MB, so four chats left open is most of a gigabyte, and this is where you find out which ones; the tiles beside it say what the agents come to, what ruri itself comes to (its window, the terminal shells, the probes that ask each harness what models it has), and what the two are of this machine's memory. Nothing is sampled unless the page is open and someone is looking at it — each reading is a `ps` over every process on the machine, and a window behind another app is nobody reading it. *What is left*: each provider's usage windows — the five-hour and the weekly, and any model-scoped one — with how much is gone and when it comes back.
- **Manga look** — Space Grotesk type, pure black-and-white UI on warm paper (deliberately low blue channel, e-ink vibes): ink borders, screentone shading, hard offset shadows, grayscale syntax highlighting that leans on weight and slant instead of hue. Statuses are shapes, not colors — rows stay clean, and a small diamond pip appears on a row only when a background turn *finishes*. Scrollbars are hairline-thin (3px) everywhere, and while a turn thinks, a two-frame hand-drawn Ruri doodle flips poses in the transcript, wiggling between little tilts in the same hard half-second steps.
- **Projects sidebar as folders of sessions**: each project is a collapsible folder holding any number of parallel sessions, and each session is auto-named by the small model the moment its first prompt goes out (in parallel with the turn, not after it) — by the ROLE it serves ("Frontend UI", "Backend API"), not the literal prompt. Star a project to pin it to the top of the list (the filled star is the only marker — no separate section); + on a folder adds a session. Folders are folded by default — new projects arrive closed, and only the ones you open stay open across restarts. Removing a session deletes its transcript and nothing else — even the last one just leaves an empty folder (only the folder's own X closes the project); files on disk are never touched. A session at work — its turn running, or agents and scripts it left running after it — has a small dragon's head where its X goes, there without a hover (a folded folder wears one for any session inside, and the Projects row one beside the number of projects at work, which is all its count shows — nothing while every project is quiet). The heads chomp on the thinking doodle's clock — jaws open, jaws shut, two drawings twice a second — and hold still when they are scrolled out of view or ruri is not the window in use. Run the pointer over a row and its head bites twice, shaking with each, and holds its jaws open until the pointer leaves. A folded folder wears the head in its own X's place while any session inside it is at work. The head still does what the X did — click it and it asks before removing anything, and says the work stops with it. Projects are opened by asking Home.
- **Persistent sessions**. Sessions start lazily on first message, run in their project's directory, and auto-restart with `resume` if they die — context carries over.
- **A chat never loses its conversation — whatever you do to it.** Switch its model back and forth across harnesses as often as you like — Claude, then Codex, then OpenCode, then Claude again — and it keeps a session on each: the harness you come back to resumes the very session it had, and is told what happened on the others while it was away; a harness the chat has never run on starts from a brief of the whole conversation. A switch while a turn runs lands after it, however many times you change your mind under it. Click away to another chat or project mid-turn, close the window, let the socket drop, leave a chat until its process is reaped, quit or crash the app in the middle of a turn or before a fresh session's first reply — the next prompt still answers from everything that was said. A session its harness no longer has (Claude's, Codex's or OpenCode's) goes the way a lost Claude session always did: the prompt goes again to a fresh session, briefed on the conversation, and the transcript says why. `bun run session-stress-test` does all of it to one chat against the real CLIs and asks for its codewords after every step.
- **App-side prompt queue** — send another prompt while a turn is running and it doesn't touch the harness at all: it waits in the app, shown as a "queued" bubble ringed in quiet dots (they fade up to ink under the pointer) you can still edit or remove, and goes out the moment the running turn (and anything queued before it) finishes. Stop holds the queue; send it explicitly or send a new prompt to resume it. So does a turn that fails for a **dropped connection or a usage limit** — every prompt behind it would only meet the same wall — and the bar under the queue says which: "the connection dropped", then "the connection is back" once ruri can reach the API again, or "usage limit reached until 9:20 PM" when the harness says when it lifts. The queue never goes on its own; **Send queued** sends it, in order, whenever you judge it should (a new prompt pulls it along too). A split prompt's unsent remainder waits there with it, as prompts you can see. To **cut in** instead of queueing — stop the running answer and send this prompt in its place — press ⌘Enter (or ⌘-click send), or hold Enter: a ring closes round the send button over 0.6s, and letting go before it meets itself queues as usual. The cut-in waits at the head of the line until the stopped turn settles, then goes out, and whatever was already queued follows it. Press a card and drag it to move it: onto another's edge takes that place in line, onto another's body folds the two into one prompt where it landed — the words in the order the two stood in the line, so the one nearer the front still reads first, pictures renumbered to match. For eight seconds the fold wears an **undo** that takes the two apart again, each back where it stood.
- **Prompt splitting** — the scissors button sends your prompt like any other: it appears in the transcript immediately, exactly as written. Behind the scenes the small model splits it into separate near-verbatim requests (strictly no invented intentions) and feeds them to the session one turn at a time, attachments following their `[image #N]` markers into the right sub-prompt — none of which shows in the UI. If the split fails or no small model is set, the whole prompt just goes out as one turn; nothing is ever lost.
- **Attachments** — drop or paste anything into the composer (25MB each): images, videos, PDFs, text/source files, whatever. A `[image #N]`/`[video #N]`/`[file #N]` marker lands in the text right where you dropped it (or at the caret on paste; spaced so nothing sticks to the brackets, and strictly inserted — what you've already typed, blank lines included, is never touched) with thumbnails above it — non-media files show a doc tile with their extension; click any thumbnail for the full-size view (PDFs render inline, text files show their contents). Drag on a full-size image to mark regions and attach a note to each — every region goes to the model as its own image, cropped with generous breathing room and the region drawn on it as a numbered white box, so the model sees both exactly what you marked and where it sits (a tight crop of empty space would mean nothing without the surroundings). Images go to the model directly — a PNG, JPEG, GIF or WebP as it is; any other picture (an SVG, a BMP, an AVIF) as a PNG the composer draws of it, with the original's path beside it so its source is there to open; one the browser can't draw either (HEIC) as a path — and a thumbnail that won't draw shows as a file tile rather than a broken frame; videos and other files are saved to disk and referenced by path for tool-based inspection. Uploads persist under `~/.config/ruri/uploads/`; one that nothing refers to any more (a rewound prompt's, a closed session's) is removed a day after it was written. Unsent drafts — text and attachments both — are kept per session, so switching sessions mid-composition and coming back restores exactly what you were writing; a save the socket was down for goes again on reconnect, bytes and all, rather than leaving the text pointing at pictures the server never got.
- **Streaming responses** rendered as markdown (GFM, syntax-highlighted code blocks with copy buttons), tool-use chips (`Bash — bun test`; absolute paths inside the project collapse to `projectname/relative/path` — a full path in a chip means the tool reached outside the project), and per-turn result lines with duration and what the turn would have cost at API prices. Interrupting a turn ends it with a plain "you stopped this response" line — never the CLI's diagnostic soup dressed up as an error. A prompt that's just a slash command (`/compact`, …) shows as an inverted command tag instead of a speech bubble; click the tag to clear it (and its result) from the transcript.
- **Agents talk to agents — across projects.** A chat's agent can message another chat's, in its own project or any other open one, and hear back. Claude chats get two tools, `list_agents` (who it may message: each chat's handle, title, what it is doing and on which model) and `message_agent`; every other harness gets the same over HTTP, `POST /talk/<chat>`. A message arrives in the other chat as a prompt in a dashed bubble saying whose it is, and queues behind whatever that chat is doing like any prompt of yours (the queue card says whose too; you can take it out, and its sender hears so). What comes back is that chat's last word at the end of the turn the message started: *wait* holds the sender's call until then (twenty minutes at most, after which it comes later instead), *later* sends it to the sender's chat as a message of its own, *none* asks for nothing. In Bypass the message just goes; in any other mode it waits on a card in the sending chat — Send it or Don't. The **talk page** (the two speech bubbles in the chat header) says who may message whom: one rule for every agent, one per project for the chats in it, one per chat — each *anyone*, *only these* (whole projects, new chats included, or single chats), or *no one*, with anything that has no rule of its own going by the one above it — and under the rules, the latest messages between agents and where each has got to. ruri keeps two chats from waiting on each other for good, and stops a chain six agents deep since you last spoke.
- **Subagents you can watch — and agents of your own.** When the model starts an agent — Claude's Agent tool, Codex's `spawn_agent`, an ACP agent's Task — the chat gets the agent's card instead of a chip: its kind and what it was sent to do, a turning ring while it works with the last thing it did (the tool it just ran, or the first line of what it just said — no model is paid to summarise it), what it came back with once it's done, and tools · tokens · time under that, "in the background" if the conversation carried on without it. The card moves along in place; it never floods the chat with the agent's words. The robot button, in every chat's header whether or not anything has started yet, opens the **agents page**, which takes the pane the way the project's other pages do, a badge counting the agents still working: every agent in the chat, working ones first, and — clicking one there or in the chat — its own conversation, live: the brief it was handed, everything it said, every tool it ran with the same patches and pictures the chat shows. An agent's own agents open on top of it; Esc steps back out, from an agent to the list and from the list to the chat. The page is also where you **start agents of your own**: write a brief, pick a model (the chat's by default), and it goes off to work in the project by itself at the chat's effort and permissions, reporting back on the page. You can tell it more once it's done, or stop it mid-work; its permission prompts show on its page and in the chat, marked as your agent's; and **Put in the composer** hands any agent's report to the chat. Your agents run apart from the chat — its model never sees them, their spend lands on the project — though while one works, its chat counts as busy in the sidebar and on the projects page. What any agent did is kept apart from the chat, one log per agent, and opens again after a relaunch; an agent whose process died with the app reads "stopped" rather than working forever. An agent that had ended and is sent on again — the model messaging a failed one to carry on, or giving a finished one more to do — picks its own card back up: it works again, "picked back up" under it, with what it was told opening the next stretch of its log. That holds across processes too: a chat whose process closed in between finds the card in its transcript. **Scripts** show here as well: a shell command the model leaves running in the background (Claude's Bash with `run_in_background`) turns from a chip into a card of the same kind, with a terminal for an icon — running while it runs, then how it exited — and it opens onto its command and what it has printed, read again every couple of seconds while it runs. Codex agents' own work shows from yagami 0.9.0, which forwards what their threads do.
- **Permission prompts**: whenever an agentic harness would ask in its own terminal, ruri shows the same Allow / Always allow / Deny card. The composer's four modes mean the same thing across Claude, Codex, and ACP agents: ask-first asks, accept-edits auto-accepts edits but still gates other tools, plan denies mutation and uses the harness's read-only/plan mode, bypass stops asking. Harness-native allow rules still apply, and "Always allow" maps back to the harness's own session/persistent choice. Native live plans from Codex and ACP agents render inline as a compact checklist that stays current while they work.
- **Per-chat model, reasoning effort, and permission mode** in the composer — a pick is that chat's alone. It lands on the session and persists with it; no other chat in the project moves, and a chat that was running on the project's old default is pinned to it before the default changes. What the project remembers is only what a *new* chat starts on: the last pick made in any of its chats. A fork keeps what it forked from. A pick made while the chat's turn is running waits: the turn finishes on what it started with, and the change lands the moment the session goes idle — before any prompt queued behind the turn goes out, so that prompt runs on the new pick. Between Claude models the live process is kept and told to switch (the CLI's own `/model`), so the conversation goes out byte for byte as before and the API reads it back from the prompt cache; switch back and the earlier prefix is still warm. Each result line records which models answered the turn and how many tokens came from the cache, and `bun run model-switch-test` proves the whole sequence against the real CLI: a switch under a running turn leaves it on its model, the next prompt answers on the new one, and switching back reads the prefix from cache. Effort is not a hardcoded global guess: each exact model's live catalog supplies its supported levels and default, the dropdown only offers those, and changing one quietly rebuilds and resumes the warm session. Claude receives its native effort, Codex receives the turn's reasoning effort (including `ultra` when a model offers proactive multi-agent work), and ACP maps it to `thought_level` when the agent exposes that option. A model with no effort control shows none. The Home composer has the same controls. Settings holds the device-wide **model catalog**: a searchable list of every model every installed harness can serve — probed live from each harness (Codex's `app-server`, an ACP agent's own model list), never hardcoded, and re-probed whenever Settings opens. Models go by their own names alone — the serving harness appears only as a tag in the catalog — and they go by their *versions*: Claude's own display names are bare families ("Opus", "Fable", "Haiku", each of which has been several different models), so the version is read back off the id the alias resolves to, or the first words of the description, and the picker says **Opus 5**, **Fable 5.1**, **Haiku 4.5**. Capability metadata — input modalities, adaptive/fast/auto support, personality, multi-agent level, service tiers and provider defaults — survives the catalog instead of being stripped at the adapter boundary. Marketing parentheticals are cut, except that a big-window model keeps a `1M` mark whenever the catalog also lists the ordinary one, since that choice is what the context gauge measures against. The Claude CLI no longer lists its `[1m]` models — the plain ones have the million-token window themselves — so a star or a role left on one moves to the plain model it lists (a chat already on one keeps it; the CLI still takes it); star the ones you actually use and every picker offers exactly those (with nothing starred it falls back to everything). The star only favourites — a second click unstars, except on a model wearing a tag, whose star is held until the tag goes to another model. The two roles, **small tasks** and **default** (what new chats and new projects start on), are tags on the rows, and the tags are handles: drag one onto another model to hand the role over in one move; the new holder is starred if it wasn't. A starred model or a role's holder keeps its row even when its harness stops listing it (named from its id), so its star and tag stay within reach. Crowning a new default moves nothing that exists — every project and chat that was riding the old default is pinned to it first — so only what you open from then on starts on the new one. With nothing crowned the default is the newest Fable; an unset model never means "whatever the CLI feels like", and there is no ambiguous "default" row anywhere.
- **Any harness, same workspace — verbatim** — the model picker also lists every other coding CLI yagami detects on your machine (Codex, OpenCode, Gemini, Copilot, any ACP agent), as `provider:model` ids. Pick one and that project's sessions run the harness's real interactive engine (Codex rides `codex app-server` — the same engine its TUI runs on; ACP agents keep a warm protocol connection), with its own config, tools, hooks, MCP servers, sandbox and approval vocabulary intact. Ruri layers only the controls you chose in the composer. Tool calls, Codex sub-agent collaboration (each spawned agent a card, its thread's own work in its log), thinking boundaries, native plans, permission requests, `request_user_input`, and MCP/ACP form or URL elicitations all cross one provider-neutral session contract; typed, optional, numeric, boolean, multi-select and secret fields retain their real values rather than being flattened into prose. Sessions stay warm across turns and resume across restarts; a harness process that dies as it starts — OpenCode exits "database is locked" when another OpenCode opens in the same moment — or one that died while the chat sat idle is opened again and the prompt goes to it, so the turn is answered instead of failing with "ACP connection closed". A chat that moves to another harness keeps the session it had on this one, and a switch back resumes it, caught up on what ran elsewhere meanwhile. `~/.config/yagami/config.json` custom providers/paths are honoured.
- **Interrupt** button to stop a running turn, and a transcript that opens at the latest message (relaunches included) and follows output only while you're at the bottom (a jump-to-latest pill floats just above the composer otherwise).
- **Edit & rewind** — hover any past prompt in an idle project session and a pencil appears on its shoulder. Rewinding puts the chat back to just before that prompt ran — everything, not just the transcript: the discarded turns leave it, the prompt returns to the composer for editing (attachments and drawn regions included), and **Rewind & send** continues from what survived. The conversation resumes at the kept exchange wherever the harness can fork there — Claude's session file, Codex's native thread at the exact preceding provider turn — so the model holds exactly what is on screen rather than a summary; a harness without a fork primitive, a compaction after the target, or a session whose fork point can't be found restarts from ruri's brief of the kept exchanges (the one `/compact` writes), and a rewind to the very first prompt simply starts afresh. The context dragon goes back with it: every turn's closing occupancy is kept, so the gauge reads what the conversation held when the kept exchange was over — not the tip's number, and not zero — and a fork opens reading what the exchange it branched from left.

- **The files go back on every harness — and only what the discarded turns did.** ruri takes its own checkpoints on whatever harness is running, twice a turn: the project's whole working tree written into git as a commit nobody can see, once as the prompt goes out (`refs/ruri/<session>/<prompt>`) and once as its turn ends (`…/done/<prompt>`). A turn's change is the difference between the two, and a rewind takes the discarded turns' changes back out of the tree as it stands, newest first — files edited, added, deleted, whether through the model's edit tools or the shell (a package installed, a generator run, a file moved), none of which Claude's own checkpoints ever saw. What happened between turns stays: an edit of your own, another chat working in the same repository. Where something else has changed a file the turns changed too, the turns' lines are merged back out of it; where the lines cross, the file goes back to how it was before the prompt, and the rewind names it. The repository goes back as well: each checkpoint writes down HEAD and every branch and tag, so a commit a turn made is taken back, a branch it made (or merged and deleted) and a tag it cut go with it, and HEAD returns to the branch it was on — unless those commits are already on a remote, or the branch has moved on since, or another worktree has it checked out, in which case it is left where it is and the rewind says why. Nothing staged by the discarded turns stays staged. Capturing never touches the repository you are working in: the commit is built through a private index file, so your staging area, your branch and `git log` are exactly as they were, and nothing is ever pushed; a tool that can change a file waits for its prompt's checkpoint to be written first. `.gitignore` is obeyed, so `node_modules` and `.env` are neither captured nor removed on the way back, and everything from just before a rewind — the tree and every commit a moved branch let go of — is kept under `refs/ruri/<session>/undo`, so a rewind is not the end of the work it discarded. Only a project that isn't a git repository falls back to Claude's own file checkpoints (for the files its edits touched), and on other harnesses the rewind says the files stayed. Checkpoints are capped per session and go when their prompts or their session do.
- **The peek band, yours to set** — Settings → Peek band: the strip of pictures across the top of the sidebar — out of the box one mountain path, by day on light, under the stars on dark and at sunset on ember — drawn at twice its size over a faint view of what the band cuts off, with the window's three buttons where macOS puts them. Any pictures — PNG, JPEG, GIF, WebP, AVIF, animated PNG, SVG (drawn out to a PNG) — up to sixteen, added with **+** or dropped on it, each sized to the band's height to start. Drag one to place it, scroll over it to size it, arrow keys to nudge (Shift for ten), or type where it goes; **Forward** and **Back** stack them. Each has its own hover: **lift**, **sink**, **grow**, **pop**, **tilt**, **spin**, **wiggle**, **bounce**, **glow** or **fade**, with a strength and a speed — hover it in the editor to see it — and **Use on every picture** hands one hover to all of them. A **hover picture** is shown instead while the pointer is on it, and a GIF there plays from its first frame every time. An animated picture plays **always**, **on hover** (resting on its first frame, starting over each time) or stays **still**; one that plays always is held on its first frame while ruri isn't the window in use. **Themes** keeps a picture to light, dark or ember, or any two of them (the stage shows the theme you're on), so a band can change with the theme; **Dark themes** swaps ink and paper for line art, or leaves a picture its own colours; **Mirror** flips it. **Restore the default** puts the mountain path back. The band is the window's title bar, and a drag region never sees the pointer — so while ruri is the window in use the band has none: every picture gets its hover, and pressing anywhere on the band (picture or gap) and dragging carries the window, the shell moving it only while the button is down (a double-click zooms, or whatever the Mac is set to do). Behind another app the band is the title bar again, so the first press drags the window natively as it comes forward. Kept as one preference; the pictures are uploads the sweep leaves alone while the band uses them.
- **Fast switching** — a session opens on its last screenful and fills in the rest behind you: the tail paints immediately, the older turns arrive on idle frames, and scrolling back pulls in more as you go. Rendered markdown is cached by its own text, so a session you've already read re-opens from strings that are already HTML, and the sessions you *haven't* opened are rendered ahead of time on idle frames — clicking one is a paint, not a parse. Measured on a 700-event transcript: 144ms to switch before, 28ms after; a first open of an unvisited 400-event session went from ~100ms to ~10ms.
- **Catch up: where the work stands** — every project keeps a working memory for the model that picks the work up cold — a fresh chat, a harness that just took over, another agent in the same project. It opens with **git's own account**, read as the file is written and again after every turn: the branch, what's uncommitted, which branches aren't merged, the last commits — facts no memory can get wrong, and an open item that names a branch says what git makes of it ("[git: feat/self-update is not merged yet]"). Then **where it stands** (in progress, just done, next), **decisions and why** (a decision without its reason is half useless), **what worked**, **what didn't and why** (so nobody tries it again), **gotchas and rules** (the traps, what the user insists on or forbids), and what's **still open**. Every line ends with the day it was learned, the exchange it came from (`7a3637b4#16` — `ruri recall show 7a3637b4#16` prints it whole, so a session can check a line before leaning on it) and who wrote it. Two hands write it: the **agent that did the work**, first-hand, from its shell (`ruri note decision "…" --why "…"`, or `failed`, `worked`, `trap`, `open`; `ruri memory` lists the lines with their ids, `ruri forget <id>` takes one out); and the **small model**, which keeps the lines it isn't changing by their ids — they come back exactly as stored — rewords only its own, never an agent's or yours, and can't drop a pinned one. `ruri recall <words>` searches every exchange in the project across its chats, and `ruri state` is git and what this chat has changed, live. It is gathered from every chat in the project, so a chat opened tomorrow knows what one closed today found out: the small model folds in what finished turns did — a project's first finished turn at once, then its turns gathered and folded together at most every ten minutes (`RURI_BRIEF_EVERY_MS`), each read long enough to catch the "tried X, it broke because Y" in the middle of a turn — merging what belongs together, taking out what got resolved and dropping what stopped mattering, so it stays a screen long. A project that already has chats reads them whole the first time: each chat's condensed digest, its recall notes and its last replies. It lands in the project as `.ruri/catchup.md`, and every session is told to read it before it starts and not to redo a settled decision or retry a failed approach without a new reason. The per-chat compaction digest keeps decisions with their reasons and what failed the same way.
- **Ideas** — a per-project board of things you want, in your own words. The tracker's opposite number: the model writes that one and you review it; nothing writes this one but you, and nothing leaves it on its own. The box an idea is written in grows with it (Enter adds it, Shift+Enter starts a new line) and takes pictures pasted, dropped or picked with the picture button, each marked `[image #n]` where it went in; whatever is in it stays there until it is added — through leaving the page and through a relaunch, kept with the composer drafts. - **A component library per project** — every piece of a project's interface on file, the way shadcn keeps a library: the **Components** button opens it as a gallery under the project's name, a search box over a grid of cards, each with its picture, the name you call it and the handle it installs by (`peek-band`). Click one for its page: the picture (drop or paste more, click one to see it whole), `ruri add peek-band` to copy, what it is, its handle, what else it's called, tags, **its files** (its own code — what an install copies), **reaches into** (the shared stylesheet or the screen it sits on, often with a line), the packages it needs, where it is on screen, and where copies of it have been installed — and under that its **code**, one tab per file, highlighted with line numbers, opening at the line an entry points to. Each project's library is its own. It holds interface only — screens, panels, cards, controls, dialogs, their styles and pictures — never backend code: nothing puts a server module in it, `ruri register` refuses one, and the first launch of this version sets aside any entry an older index held that had no interface in it (kept in `components/<projectId>.not-ui.json`). Agents use it from their shell with the **`ruri` command** ruri puts on every project session's PATH: `ruri search <words>` and `ruri list` to find what exists, `ruri show <slug>` for one in full with its code, `ruri add <slug> --dir <folder>` to copy it into place (the folder is remembered per project — the page shows and edits it — so later adds need no `--dir`; a file already there is left alone unless `--overwrite`; the packages it needs come back as the install command for the project's own package manager), `ruri add <project>/<slug>` to take one from another open project's library into this one's, `ruri register` to put back what they build, `ruri edit`, `ruri remove` and `ruri dir`. It is a few lines of sh posting to ruri (`POST /library/<chat>`), so it works the same in every harness with nothing but curl. Claude sessions also carry the library as a skill, `ruri:components`, in a plugin ruri keeps per project: its description never changes, so the session's prompt stays cached however often the library does, and its body — the list — is rewritten whenever the library changes (Claude reads a skill's body once a session, so it points at `ruri list` for anything added since). Entries still arrive the way names always did: a session that has just built something calls ruri's naming tool (`mcp__ruri__name_component`, now with a handle, its own files, the places it reaches, tags), and a card comes up in the chat — *"I made something for the library. What do you call it?"* — with its suggested name, **a screenshot of the thing**, its files and a line on what it is; the picture is the point, since a filename and a sentence are what the model has and neither is what you recognise. ruri copies the picture into its uploads as the card goes up and keeps it with the entry. Edit the name to whatever you'll actually say, hit **Name it**, and that's the name from then on; **Skip** writes nothing; in Bypass the entry is written straight away. The library reaches the model as `.ruri/components.md` in the project, as the skill, as the `ruri` command, and — for a prompt that names an entry by name, alias or handle — as that entry carried down with the prompt on the model's copy only. **Update everything** keeps the library true to the code and fills it in. It follows an entry's files through git's renames and drops the ones that are gone — an entry whose own code is gone altogether is retired, kept in `components/<projectId>.gone.json` — then reads git for each entry's commits and uncommitted edits since its picture and note were current (tests, docs, chores and reformatting don't count, nor commits within the hour after a picture, which are the work it already shows). For everything built before any of this, it reads the repo's interface files (the small model, so any harness) and names each piece of interface nobody has named, with the CSS class each one sets; it only re-reads files touched since the last run. The small model then reads what changed under each entry that fell behind, rewrites notes the code has outgrown, and says whose look changed. Last, pictures, for every entry without a current one: first mechanically — the project started with its own dev script, opened in a window nobody sees, each component photographed by its selector (the **on screen** field takes the whole path, `/settings >> .tab >> .panel`), refusing a picture of nothing — and then, for whatever that can't reach (behind a click, a login, a state the app doesn't boot into, an app that isn't a page), a **Library pictures** chat in the project: an agent that runs the app beside your own copy, drives it to each one with the bridge, photographs it and files it with `ruri edit <slug> --shot`. Pressing it again reuses that chat, and waits for it while it is still at work. Pictures are newest first — a new one is the one shown — and a turn that edits an entry's own files marks it changed as it ends, unless the turn also took its new picture; a card whose code moved on after its picture says **outdated**, and its page says when. Sessions are told to update what they change (`ruri edit <slug> --shot <new screenshot>`), and naming one again under its own name or handle updates it rather than adding another. New entries wear a spinning star: beside the name for what the last prompt named, hooked over the card's corner for what has been waiting longer, and on the Components button itself. Looking is what takes it off — hover one, open it, or leave the page. Esc goes back from a component to the gallery; `/` searches it.
- **The vault** — passwords, tokens and the accounts they belong to, held by ruri so the model can *use* them without ever *reading* them. Add one in Settings (name, optional username, the value, what it's for); the value is written to `~/.config/ruri/secrets.json` at 0600 and never crosses the wire again. Claude can write `{{name}}` into a command or file and a PreToolUse hook swaps the value in after generation but before execution. Every harness also inherits `$RURI_SECRET_NAME` (and `$RURI_USER_NAME`); non-Claude briefings name only that path, rather than falsely promising a placeholder hook their protocol cannot provide. Anything a value leaks back into — a command's output, a permission card — is redacted to its handle before it reaches the transcript or the screen. Neither path can stop a model that deliberately prints one, which is why it is told not to and why the redaction exists.
- **Harnesses that keep themselves current** — Settings → Harnesses lists every coding CLI on the machine (Claude Code, Codex, OpenCode, Gemini, Goose, …) with its version, the newest out, and how it was installed. ruri looks on the hour and brings each one up to date the way it came — its own updater, bun, npm or brew — never while a chat on it is mid-turn; a chat warm on the old binary picks up the new one with its next prompt. Untick **by itself** to update one by hand (its **Update** button, or wherever it came from); **Check now** looks at once. Anything installed some other way is shown and left alone.
- **Integrations** — Settings → Integrations shows what Claude Code and Codex plug in, as their own CLIs keep it: every MCP server (everywhere, or — with a project picked — that project's own, just yours or shared through its `.mcp.json`, and the ones plugins bring), every installed plugin, and the marketplaces they come from. Add a server (a command, or a URL, with its environment or headers), take one away, install a plugin from a search of the marketplaces, turn a Claude plugin off, add or remove a marketplace — each is that harness's own CLI doing it (`claude mcp add-json`, `codex plugin add`, …), so a change is exactly one made in a terminal. Listing starts nothing (`claude mcp list` would start every server to check it), and what a server is given shows by name only — the values stay in the harness's config. A chat picks a change up when its harness next starts: warm ones restart as each goes idle and carry on where they were.
- **Skills** — the folders of instructions a harness reads before it works, in both scopes: `~/.claude/skills` for every project on this machine, `<project>/.claude/skills` for this one only. The page lists what's installed with where it came from, installs and removes through [`bmo`](https://github.com/justin06lee/bmo) (any source bmo takes — repo, folder, zip, url), and updates them all in one press. Click a skill's name and its SKILL.md opens rendered — headings, lists, code blocks, the lot — because a skill is prose and reading it as a file is not the same as reading it. Off is ruri's own word for it, since neither Claude Code nor bmo has one: the folder moves to a sibling `skills-off/`, out of the tree the harness scans, and straight back when it's turned on again — nothing is deleted. Claude Code loads a project's local skills itself; every other harness is told they exist and where to read one.
- **Shells in the composer** — the `>_` button turns the prompt box into a terminal in that project's directory: your login shell, your rc files, your prompt, your colors, on a real pty. A numbered tab row across the top opens as many as you need (`⌘T` for another, `⌘1–9` to switch, `×` to close); every one keeps running while you're elsewhere, so switching back finds them where you left them. The tab row itself outlives the app — reopening the panel finds the same row, each tab starting a fresh shell the first time it's looked at — and the shells die with the project.
- **Three themes, on a clock** — light (paper), dark (the same page at night), and ember: warm through and through, no blue channel to speak of, for late sessions. Settings can hand the choice to the clock, on a dial: one turn is one day (24 hours, not 12 — the thing being set is a whole day, and half of it would otherwise sit behind an am/pm switch), and the ring around it is painted in the three themes, each stretch in that theme's own paper and edged in its own ink, so the evening looks like the evening while you're reading it in daylight. Drag a mark round the ring to move a boundary, or nudge the times beside it for exactness; a hand shows where the day is now. Picking a theme by hand turns the clock back off. The theme, the clock, which folders are unfolded and the player's volume are the window's preferences and are kept on the machine (`~/.config/ruri/prefs.json`), so they come back the way you left them; the window's own storage is a cache in front of that, for the theme to be on the page before the first paint.
- **Rapid fire** — the bolt row under Home turns the main pane into assembly-line prompting for parallel work. It shows one session at a time, whichever is ready for a prompt, as the ordinary chat page — the full transcript, the real composer, everything where you expect it — with the line's controls in the header. The sidebar doesn't move: the app's own session stays selected, and leaving the line puts you back on it. Its controls — how many are ready, skip, leave — sit just above the composer rather than in the header, which belongs to the project. Send, and the prompt lands and sits there a beat, the card eases out, and then the next project announces itself — its name in large type, and its session's role under it, held long enough to register — before its chat rises into place behind the name. You never have to look up at the header to know where you are. Skip passes to the next one; a session that's working is passed over until it finishes, and when everyone's working the card stays where it is so you can watch that turn end. The star on the plate says who is in the line: filled, only the starred projects; hollow, every open one, starred first. It is remembered across launches, and narrowing to the starred when nothing is starred says so (“nothing starred”) rather than counting to zero. Hidden projects are never in the line either way — out of the sidebar means out of the rotation, and `web/src/lib/rapid.ts` is tested on exactly that.
- **Music player** in the sidebar (ported from `home`): point Settings → Music at any folder (default `~/Music/ruri`, or `RURI_MUSIC_DIR`) — each subfolder is a playlist, loose files are "Unsorted". Two-deck Web Audio engine with 6s equal-power crossfade, shuffle, seek, volume, and a repeat button that cycles off → loop the playlist → loop the current track (a little "1" marks track mode; deliberately session-only — every launch starts with repeat off); tracks stream from ruri's own server with Range support. While a track plays, a five-bar waveform fed by a real analyser tap on the master output rides the gap between the track title and the chevron (the note icon stays put), and little notes wobble upward from the player bar. The engine only runs while something plays: pausing stops its frame loop and crossfade scheduler and lets go of the audio device, and pressing play starts them again.

- **Whose model, doodled** — over an empty chat (Home, or a fresh project chat) sit the marks of whoever made the model it runs on, drawn as if in felt-tip in a notebook margin: Anthropic × Claude, OpenAI × ChatGPT, Google × Gemini, xAI × Grok, Moonshot × Kimi, Alibaba × Qwen, Z.ai × GLM, Mistral × Le Chat, Meta × Llama, DeepSeek's whale × its name, MiniMax × its name. The lab comes from the model: an OpenCode provider that names one, else the model's own name (so OpenCode's gateway serving Muse Spark gets Meta's), else the harness that only runs its maker's models; with none to go on it's the harness's own mark (OpenCode, Goose) × the model's name lettered by hand. Outlines follow the theme's ink in light, dark and ember; the brand colours sit a hair off them like a misregistered print; each mark has its own tilt and wiggles under the pointer (not with reduced motion). Pick another model before the first prompt and the marks change with it. The same doodles, small, stand beside every model's name in the composer's model picker (on its trigger too), the agents page's picker and Settings' model list — the product's mark (Claude's spark, ChatGPT's tile, Gemini's sparkle…), the lab's where the product is only a name (DeepSeek's whale, Z.ai, MiniMax), else the harness's own.
- **Home says sup.** — over Home's empty chat, a greeting; over a fresh project chat, its title. **Settings → Greeting** holds Home's lines: one is always said, several (one to a line) take turns, a new one each launch, and an empty box means no title at all. Up in the title bar sits the **peek band** — see below.
- **The dragon gauges** — four dragons flank the composer, each filling from his feet up, and past 80% he starts sweating. Left of the box: how full the session's context window is, and the 5-hour window. Right of it: the weekly window across every model, and the weekly window scoped to one model, which the account names itself ("Fable", "Opus"). Under each name is how long until that window rolls over — *in 2h 41m*, *in 6d 22h* — because the percentage answers how much is left, not how long until you get it back; hovering gives the reading in full, with the date. They belong to whichever harness the session's model runs on, never to Claude by default: Claude's come from the same endpoint Claude Code's own `/usage` uses (your existing sign-in, no second one), Codex's from the windows it writes into every session rollout on disk, and a harness that reports neither shows empty dragons rather than somebody else's numbers. The last good reading is kept on disk, so a relaunch opens on numbers instead of four dashes. The context gauge counts the whole window — everything sent, cached or fresh, plus what came back — measured against the window that channel's model actually has — the size the harness reports with each turn (Claude's CLI and Codex both do; plain Opus 5.5 reports 1M), remembered across relaunches from what earlier turns on that model reported, or, before any turn on that model has ever said, 1M on a `[1m]` model and 200k otherwise — and 1M whenever the chat already holds more than 200k, so a big chat switched onto a model is never drawn full. The dragons are always there: over an empty chat too, and in a narrow window they stand smaller rather than go.
- **Feature tracker** — the small model splits each prompt you send into its distinct requests — one checklist item per request, in your own words, nothing invented or embellished (it never sees the replies) — the moment the prompt goes out, so a stopped turn or a "continue" follow-up can't lose requests and nothing from a long prompt gets forgotten. Items stay tied to the prompt they were split from: edit & rewind a prompt and its auto items (plus those of every discarded later prompt) vanish, then the edited prompt re-extracts fresh ones on send — the checklist always mirrors the prompts that actually stand. Manual items are yours and never touched. The header's tracker button swaps the whole chat pane for the **todo page** (no navigation — the same lit button swaps back), and the page opens itself when new items land. Reviewing is one pass: click anywhere on an item — once for works (check), twice for needs-work (x), which smoothly folds out a note field (foldable again to stay focused) — and items never move while you review. Notes save on blur *and* on the way out, so closing the page mid-thought loses nothing. Paste or drop files straight into a note; they show as little numbered bumps on the textbox's top edge (click one to remove it). **Finish review** then clears the checked items, reopens the crossed ones pinned at the top with a repeat badge on their checkbox (new extractions land below them), and assembles one fix-it prompt mechanically — each crossed item's title with your note verbatim under it, note attachments as stored file paths for tool inspection; no model call, so it's instant and exactly what you wrote — dropped straight into the composer (persisted as that session's draft, so it survives switching around). Persists in `~/.config/ruri/tracker/`.
- **Dropped turns go again, always.** A turn the API drops — overloaded, a 5xx, a cut connection — is picked back up by ruri itself: a short wait, a nudge down the same session (which still holds the whole conversation), three tries backing off over about a minute and a half, and the work carries on from where it stopped. A dropped connection is waited out rather than timed: the try goes once ruri can reach the API again (a TCP handshake every ten seconds, nothing sent), however long that takes. A usage limit is never tried again. Anything you send or stop cancels the wait. There is no switch for this: an overload is weather, not a decision.
- **Turns the harness starts itself.** A background task that ends between turns wakes Claude Code to answer it — a turn nobody sent. ruri counts it as a turn: the chat shows as working, prompts you send meanwhile queue behind it, and its process is not closed from under it (the model hears its task finished, even with the chat open nowhere). A prompt that reaches the CLI while one of those is starting waits its turn there, and the result it gets is its own: each prompt is echoed back the moment the CLI takes it up, and a result that comes before that echo is folded into the prompt's turn rather than signing it done.
- **Turn memory** — a small model writes two terse recall notes per exchange, telegraphic to the point of caveman ("header flickers on scroll; shrink logo"): the prompt's, the moment you send it, and the reply's, the moment the turn finishes. Which model: drag the inverted "small tasks" tag onto one in the Settings catalog to crown it the **small-tasks model** (any harness works — yagami routes qualified ids), used everywhere the small model runs (recall notes, session role titles, prompt splitting, the tracker); with no model holding the tag it's `RURI_SMALL_MODEL` or GPT Luna, and `RURI_NO_MEMORY=1` disables the layer. A small model runs on somebody's subscription, and subscriptions run out: when the chosen one fails (Codex's "you've hit your usage limit" lasts hours), the call goes to the other harness's cheap model — Haiku for anything that isn't Claude, GPT Luna for Claude — and the spent one is passed over for ten minutes rather than made to fail again on every call. A note that still goes missing (both out, offline, the app quit mid-call) is written later, three at a time in the background: the whole backlog five seconds after launch (and hourly after that, when there is rarely anything left), with a chat that opens or compacts going to the front — so a chat's notes are there before it's opened, rather than arriving while you look at it. A note is checked before it is kept: a small model handed a message that talks about compression, or one that reads as if addressed to it, will sometimes review it ("this isn't a message to compress") or answer it ("I can't see images") instead of compressing it — a note that is longer than its source, asks a question the source never asked, or uses the job's own words when the source didn't is asked for once more with the failure named, and a second miss is dropped so compaction falls back to a plain cut of the text. The notes stay out of the way — turns always show in full, and nothing below the newest compaction mark folds at all: no chevron, no dotted edge under the pointer, since an exchange still in the conversation has no notes to fold to. Above the mark, a hover chevron on a turn's top-left folds it down to its notes, laid out like the chat it stands for (the prompt's note in a bubble ringed in quiet dots, the reply's under it). Each half opens on its own — click the prompt's note for the whole prompt, the reply's for the whole reply, "full exchange" for both — and the view goes to the top of what opened, to read it from the start. Transcripts, notes, and the resumable session id persist in `~/.config/ruri/sessions/`, so history and context survive app restarts.
- **The architecture: the stack as an index, a sheet per layer** — the project's shape, for a model that has never seen it, in two levels so it stays short however big the project gets. `.ruri/architecture.md` is the **index**: what it is and who it's for, **the stack as layers** from what a person touches down to the engines underneath (each with what it does and what it owns), **how it flows** across the layers, what it can do, where things are, how to run it, and the conventions a session must follow. Every session in the project is **shown the stack before it starts** — a line a layer, its name, its handle and what it does. Each layer with code of its own has **a sheet behind it**, `.ruri/layers/<handle>.md`: where to change what inside it, how work moves through it, its key files, its rules and traps, and what it talks to — and a session reads the sheet of the layer it is about to work in, and none of the others (`ruri layer <handle>` prints one; `ruri layer` lists the stack). The small model writes it all from a read of the repo — README, manifest, Makefile, CLAUDE.md/AGENTS.md, the tree, the openings of the files that matter — and then each layer on its own, from every path it owns and the openings of its central files. The stack is cut fine enough to have a sheet a layer: a layer owning more than 30 files is cut into its parts by what they are for (a backend becomes sessions, memory, the bridge…; test scripts become integration tests named as such), and every file ends up owned by exactly one layer — what the read left to nobody is placed by the model, or beside its neighbours. Finished work folds forward **layer by layer**: a turn goes into the sheets of the layers whose files it changed, the busiest three at most, and into the index only when it changed the stack. A sheet from before layer sheets is read whole from the repo the first time one of its turns is folded, and what it knew of where to change what goes on to the layer owning it. The **Architecture** button in the chat header draws it for you: the project's name and purpose, the stack as bars top to bottom — each bar with a sheet opening it underneath, exactly what an agent gets — each flow as boxes and arrows, where things are, how to run it, what it does, with **Read the repo** (which says how many commits ago it last did) to write it afresh. Hover any line, in the index or a layer's sheet, to rewrite or strike it. The page draws the shape only — where the work stands lives in `catchup.md`.
- **Chats from outside ruri.** Under each project's sessions sits a "recent chats" row: unfold it and ruri lists the sessions on disk for that directory that it did not make — a `claude` run from a terminal, a `codex` one — newest first, titled by the first thing said, tagged by harness. Click one and it becomes a session here: its conversation on screen as a transcript, and the next prompt resumes the real thing (when the project runs on the harness it ran on; otherwise it continues from a brief of it). Every id ruri's own chats have ever run on is remembered, so nothing ruri made is offered back to it.
- **Questions never go to a hole.** Claude's `AskUserQuestion`, Codex's `request_user_input`, and MCP/ACP form or URL elicitations share the question box. The card asks one question at a time, preserves drafts across session switches, and Enter advances a typed answer (Shift+Enter inserts a newline). Required and optional fields, exact option values, numbers, booleans, multi-selects and secrets round-trip back to the native call; a secret answer is a password field and is never written into the transcript. If a Claude tool call stops waiting first — the turn ended, or the CLI gave up on the hook — its card stays, says so beside its title, and your answers go out as a new prompt of their own rather than into a call nobody is listening to.
- **Fork a chat at any exchange.** Under the pencil on every prompt sits a branch: click it and a new session opens in the same project holding everything through that exchange, titled after the original, and carries on from there — the original is left exactly as it is. Claude forks its CLI session at the kept message; Codex forks its native app-server thread at the provider turn recorded for that exchange (including every silent sub-turn produced by prompt splitting). Both keep the real model context, and a fork at the latest exchange branches at the tip. - **A sketch pad.** The pen next to the composer's shell toggle opens a pad across the pane: pen, arrows, lines, boxes, ellipses, text, five colours, three widths, undo (⌘Z), keys for every tool. The pad is the theme's own paper and the pen starts in its ink — cream and black in light, near-black and white in dark, dark and amber in ember — and the three accents are lifted on the dark themes; a drawing keeps its colours by name, so it follows the theme, and what Attach puts in the prompt looks like the pad did. **Attach** puts the drawing in the prompt as an image like any other — marker, thumbnail, the lot — because half of what is hard to say about an interface is easy to draw. The pad also opens any image from disk to draw on. Shapes are kept as shapes and redrawn, so undo is exact and the export is drawn fresh at full size. - **Selection flags.** Double-click a word in the transcript (or drag out any selection) and a flag stands at each end of it. - **Markers are chips.** An attached file's `[image #1]` in the prompt draws as a chip over the words — hover it and it inverts and its thumbnail in the strip lights up, drag it and it moves to wherever you drop it (snapping to a word boundary), click it and the attachment opens in the viewer. A slash command standing on its own (`/compact`, `/anything`) becomes a chip the moment a space follows it — while it's still being typed it stays words, and a path, a quoted mention or a URL never turns — and clicking a command chip takes it out. A word never touches a chip: type straight against one and a space is kept between them (punctuation may sit against it, so "see [image #2]." still reads as a sentence), and two chips side by side are held further apart than two words would be — solid ink needs more air than letters do, and the extra space is the composer's, not the prompt's: it goes out as one. The pill is painted a little outside its characters, and the mirror keeps room on either side to paint it, so a chip starting a line is never cut down its left edge. Backspace right after a chip (or Delete right before it) removes the whole marker, never half; removing an attachment with its × removes its marker and its regions' markers from the prompt. Underneath it is still plain text in a plain textarea: the chips are a mirror of the prompt laid over the box, shaped by the box's own computed style and moved with its scroll, so it wraps exactly where the box does (the space inside a marker is a non-breaking one, so a marker is never wrapped in half, and it goes out as a plain space). A prompt keeps its chips once it leaves the box: the same pills in the queue card while it waits its turn, and in the transcript once it is sent — where a click on one opens what it stands for, and the brackets are still there, invisible, so a prompt copied back out comes with its markers whole. The box refits itself to its words whenever it is laid out again, not only when you type — a wider window needs fewer lines for the same prompt — and should the two still disagree on the line count, the chips step aside rather than stand on the wrong words, and come back the moment they agree again. The box keeps its height, caret and scroll across a trip to the shell.
- **The bridge — a session sees and drives what it built.** After a model changes an interface, it can look at the result instead of merely asserting it — without ever interrupting you. `mcp__bridge__web_open` loads a page (a dev server, a built file, any URL) in a browser window ruri owns and keeps hidden; `web_click` (by CSS selector, by the visible words on a thing, or at coordinates), `web_type`, `web_press` (chords like `Meta+A`), and `web_scroll` drive it with real input events, so React and every handler see a genuine pointer and keystrokes; `web_wait_for` (selector, text, URL, or network idle), `web_eval` and `web_logs` (console and network ring buffers) read it; `web_screenshot` photographs it — and every driving tool returns a fresh scaled screenshot inline, so the model sees what it just did. `app_launch` does the same for desktop apps: a dev-built Electron app (started with a debugging port and driven over CDP, `app_click`/`app_type`/`app_eval`/`app_screenshot`) or any macOS app (`open -g`, driven through the Accessibility tree — `app_ui_tree` dumps the front window's controls, `app_ui` runs AppleScript UI scripting like `click button "OK" of window 1`, `app_screenshot` photographs it even behind ruri via the window server). Nothing appears in front of you, nothing steals your focus, and you can't accidentally touch the thing under test. What you get is a small live preview above the composer — the **bridge strip** — with the title, the address, a **Take over** / **Give back** toggle (take over and the real window comes forward for you to work in; give it back and it hides again with the session still driving), and a close. Whatever a session opened or launched is closed a few seconds after its turn ends, unless you have taken it over; give a taken-over window back while nothing is running and it closes the same way. The model is told so, and opens the page again in a later turn if it needs it. Claude holds the tools in-process (auto-allowed); every other harness gets the identical set over HTTP at `POST /bridge/<channelId>`, the channel id a capability told only to that session. Persistent per-project login cookies, never your own browser's. First use may prompt for macOS **Accessibility** and **Screen Recording** (needed only for driving and photographing native apps); Settings → Permissions shows whether they are held and asks again on demand.
- **ruri's own `/compact`** — type `/compact` and ruri compacts the session itself instead of letting the harness do it, instantly and at zero model cost: the live session is retired (resume id cleared — the next prompt opens a brand-new session with no context beyond the brief), every prior exchange's full record — prompt, response, tool activity, and preserved attachment paths — is written to `~/.config/ruri/turns/<session>/NNN.md`, and a brief is built from the precomputed recall notes as strict prompt/reply pairs — `user:` then `you:` per exchange, oldest first — each ending with its exchange's file path so the fresh model can Read the full record whenever a note isn't detail enough, then open any referenced image to see its actual pixels. It doesn't give every exchange the same weight: it opens with **where things stand** as git and the transcript record them — the branch, what's uncommitted and unmerged, the files the conversation changed, what the last reply offered to do next and what git says of the branches it names — and the **last three exchanges come at length**, your words exactly as you wrote them (they are what "this" and "that" in your next prompt point at) and the close of each reply. And when the brief goes out it knows the prompt it rides with: the earlier exchanges and memory lines that share its words are added at length too, the long-folded ones included — picked without a model call, so the send stays instant. The list stops at the newest 40 exchanges: past that, the small model folds the oldest into a **digest** — one condensed memory (what was built, the rules you set, what's still open) that the brief opens on, with the range of record files it covers — so a long chat's brief stops growing with every compaction (this one's went from about 11,700 tokens to 4,700). The fold runs in the background after each reply, so `/compact` never waits on it. The brief rides invisibly on your next prompt. Commands written *inside* a prompt run first: `/compact` on its own line (or as a word anywhere — it takes no arguments) and any installed skill or custom command on its own line (`/simplify web/src`) are lifted out and run in order, and what's left is sent after them as the prompt — so you can `/compact` in the middle of writing a long prompt without losing your place. Quoting one (`'/compact'`, `"/compact"`, `` `/compact` ``) makes it a mention, sent as words. Type `/` at the start of a word and the **command menu** stands over the composer with everything that would actually run — ruri's own, the handful the harness answers, every installed skill, every custom command file in `.claude/commands` — each with a line on what it does and where it comes from. Arrows move, Enter or Tab takes one (it lands with the space that finishes it, which is what turns it into a chip), Escape puts it away. The textarea keeps the caret the whole time. The transcript keeps your full history and just shows a uniform zigzag line — "compacted", in the result lines' own voice — at the break; click the label and the pairs unfold as a clean numbered list (your note in ink, the reply's under it in soft) instead of raw model text. Works on any harness, since it's all app-side. The chat collapses at the same moment: everything above the new mark folds, and stays on screen folded — each exchange as its two recall notes, laid out like the chat itself (your prompt's note in a bubble ringed in quiet dots, the reply's beneath), with the older compaction marks between them. Under the pointer only the note you're on lights, fading up rather than snapping, so what lights is what a click opens. Click the prompt's note or the reply's and that half opens alone, in place, with the view at its top, and it folds back the way it came: a prompt on a click on its bubble, at once (under the pointer it takes the note's dotted edge, so the click is no surprise), a reply by the "fold reply" pill that heads it — held at the top of the view the whole way down a long reply, and hovering it dims the reply it would fold, so tool chips never get in the way and nothing folds by accident; folded from halfway down, the view goes back up to the note. "Full exchange" opens both, and the chevron folds them again. Your own prompt folds on a click anywhere in the chat; a reply that was open from the start has no pill, and folds only by the chevron. New prompts after the mark show in full, as always. On disk the same split happens — the live transcript runs from the newest mark, and everything before it moves to an append-only history — so every save during a turn rewrites only the part since the last compaction.
